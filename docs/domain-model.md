# Domain model

## Money

`Money` is a Java `record` of `BigDecimal amount` and `java.util.Currency currency`.

- **Never `double`.** `0.1 + 0.2 == 0.30000000000000004` in binary floating point. Financial
  arithmetic must be exact decimal arithmetic. An ArchUnit rule fails the build if any field is
  `double`/`float`.
- **Normalised scale.** Amounts are stored at the currency's minor-unit scale (2 for EUR, 0 for
  JPY), so `25` and `25.00` are `equals`. Values that would need rounding (`10.005 EUR`) are
  **rejected**, not rounded. Silent rounding is how money disappears.
- **Currency-safe arithmetic.** `add`, `subtract` and `compareTo` throw `CurrencyMismatchException`
  across currencies.
- **Strings on the wire.** The API serialises amounts as strings (`"25.00"`) so no client parses
  money into a float. Requests are parsed straight into `BigDecimal`.
- **Database:** `NUMERIC(19,4)`, which leaves headroom for currencies with 3 minor digits later.

## Customers and accounts

```
Customer ──┬── Wallet EUR   (CUSTOMER_WALLET)
           ├── Wallet USD
           └── Wallet GBP

Platform ──┬── EXTERNAL_FUNDING  EUR / USD / GBP   (may go negative)
           └── PAYMENT_HOLDS     EUR / USD / GBP
```

| Entity    | Key fields                                                                        |
|-----------|-----------------------------------------------------------------------------------|
| Customer  | `id UUID`, `email` (unique, case-insensitive), `fullName`, `status` ACTIVE/SUSPENDED |
| Account   | `id UUID`, `customerId` (null for system accounts), `type`, `currency`, `status` ACTIVE/FROZEN/CLOSED, `balance`, `version` |

- UUIDs are generated by the application and exposed externally; there are no sequential ids
  to enumerate.
- One wallet per customer per currency (partial unique index).
- **System accounts** make the books close. A deposit is *DEBIT external-funding, CREDIT wallet*,
  so `EXTERNAL_FUNDING` carries a negative balance equal to all money ever deposited, and the
  sum of all balances in a currency is always exactly zero.
- Status rules: only ACTIVE wallets can send money or receive transfers. CLOSED requires a zero
  balance and is final. System accounts cannot change status.

## Ledger

```
ledger_transactions (id, reference UNIQUE, type, created_at)
        │ 1..n
        ▼
ledger_entries (id, transaction_id, account_id, direction DEBIT|CREDIT, amount > 0, currency, created_at)
```

- Sign convention, identical for every account: **`balance = Σ credits − Σ debits`**.
- `LedgerTransaction.record(...)` is the only factory and refuses fewer than two postings or any
  currency whose debits ≠ credits.
- `reference` is unique, so each business event can be booked at most once:
  `TRF-<transferId>`, `PAY-<paymentId>-AUTH`, `PAY-<paymentId>-CAPTURE`, `DEP-<uuid>`, …
- Entries are `@Immutable` in Hibernate and append-only in PostgreSQL (triggers).

See [ledger-invariants.md](ledger-invariants.md).

## Transfers

`Transfer(id, sourceAccountId, destinationAccountId, amount, currency, status, ledgerTransactionId)`.
Booked synchronously in one transaction, so a committed transfer is always `COMPLETED`.
`PENDING` only exists inside the booking transaction.

Validation (in this order, balance-dependent checks **after** taking locks):

1. amount > 0 and representable in the currency (400)
2. source ≠ destination (422 `SAME_ACCOUNT`)
3. both accounts exist (404)
4. both are customer wallets (422 `NOT_A_WALLET`) and ACTIVE (422 `ACCOUNT_FROZEN` / `ACCOUNT_CLOSED`)
5. currencies of source, destination and request match (422 `CURRENCY_MISMATCH`)
6. sufficient funds (422 `INSUFFICIENT_FUNDS`)

## Payments

```
CREATED ──► AUTHORIZED ──► CAPTURED ──► PARTIALLY_REFUNDED ──► REFUNDED
   │            │              └───────────────────────────────▲
   └────────────┴──► CANCELLED
```

| Step      | Ledger movement                                   |
|-----------|---------------------------------------------------|
| authorize | payer wallet DEBIT → PAYMENT_HOLDS CREDIT          |
| capture   | PAYMENT_HOLDS DEBIT → merchant wallet CREDIT       |
| cancel    | PAYMENT_HOLDS DEBIT → payer wallet CREDIT (only if authorized) |
| refund    | merchant wallet DEBIT → payer wallet CREDIT        |

- The transition table lives in `PaymentStatus` as data (`EnumMap<PaymentStatus, EnumSet<…>>`)
  and is tested exhaustively (every from/to pair).
- Invalid transitions return **409** `INVALID_PAYMENT_STATE` (e.g. `CANCELLED → CAPTURED`); capturing a payment that was already captured (`CAPTURED`, `PARTIALLY_REFUNDED`, `REFUNDED → CAPTURED`) returns the more specific **409** `PAYMENT_ALREADY_CAPTURED`.
- Commands are a **sealed interface** of records:

  ```java
  public sealed interface PaymentCommand
          permits AuthorizePayment, CapturePayment, CancelPayment, RefundPayment { … }
  ```

  `PaymentService.handle` switches over it with pattern matching and **no `default` branch**:
  adding a fifth command without handling it is a compile error.
- Refunds may be partial; the total can never exceed the captured amount (enforced in the
  entity and by a `CHECK (refunded_amount <= amount)` constraint).
- Every transition first takes a row lock on the payment, so concurrent captures are serialised:
  exactly one succeeds, the rest get 409.
